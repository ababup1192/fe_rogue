# sprite_stress 計測記録

環境: この Mac (Apple Silicon) / vsync off / design 320x240 / スプライト半分は単色矩形・半分はテクスチャ + SDF テキスト約300文字。

計測の流儀: **A/B は必ず背中合わせで取る**。重い区間(N=10000 等)を回した直後は熱スロットリングで
4 割方遅く出る(下の「初回スイープ後の再計測」が実例)。単独の数値でなく同条件ペアの差だけを信じる。

## 改修前ベースライン (2026-07-14, 300frame/区間, 初回スイープ)

| N | avg | p99 | fps |
|---|-----|-----|-----|
| 500 | 16.67ms | 19.16ms | 60 |
| 2000 | 87.83ms | 100.04ms | 11 |
| 5000 | 416.47ms | 446.87ms | 2 |
| 10000 | (計測打ち切り) | — | ~1 |

- **N=10000 はだいぶ無理がある**(ユーザー判断で打ち切り): 1 フレーム 1 秒前後かかり、区間完走に数分を要した。以後のスイープから除外。
- 参考: N=10000 直後の再計測は 122.8ms/600.4ms (N=2000/5000) まで悪化 = 熱による水増しの実例。

## 段階2 (インスタンシング一括描画) 単独の A/B (2026-07-14)

- **これも効果ほぼゼロ** (N=2000: 96.0→85.1ms / N=5000: 433.9→404.3ms、ドローコール数千→数個なのに変わらず)。
- スレッドダンプ 8 本のサンプリングで真犯人が確定: フレーム時間の約 8 割が
  `List.sortBy` (実体は Array.sortBy のクイックソート) と `RecordExtend.lookupField`。
  つまり **毎フレームの zIndex ソートで、1 比較ごとにキー関数がタプルを作り
  レコードのフィールド連結リストを歩くコスト**が支配項だった。GL は最初から脇役。

## 段階3 (zIndex ソートを比較レスの安定バケツ分配 stableByZ に置換) + 段階2 の合算 (2026-07-14)

| N | 改修前 | 改修後 | 倍率 |
|---|--------|--------|------|
| 500 | 16.5〜22.6ms (44〜60fps) | **3.1〜3.4ms (290〜320fps)** | ~6x |
| 2000 | 88〜96ms (11fps) | **6.8〜7.2ms (140〜148fps)** | ~13x |
| 5000 | 404〜434ms (2fps) | **16.5〜16.7ms (60fps)** | ~25x |
| 10000 | ~1000ms (~1fps) | **27.3ms (37fps)** | **~37x** |

- ソートが消えた後はインスタンシングが効く領域になる(数千ドローコールの提出費を残さない)ため、両方を残す。
- 60fps ライン: 改修前 N≈300〜400 → **改修後 N≈5000**。東方級(2000〜4000)・VS級(1000〜3000)が射程内。
- 教訓: **推測より jstack**。「ドローコール固定費 44µs」という筋の良さそうな仮説が2連敗し、
  スレッドダンプ 8 本で 10 分で真犯人が出た。次に描画が遅い時はまずサンプリング。

## 第二弾: style を instance 属性に載せてバッチ化 + instance を Float32 配列運搬 (2026-07-14, main 0.1.7 マージ後)

jstack 再計測で「Render.box は常に style=Some(solidStyle) を付ける → 全単色矩形が styled 扱いで
バッチから弾かれ per-draw のまま」と発覚。instance 属性を 16→32 floats に拡張して style
(角丸・枠・ハッチ) ごとバッチに載せ、run を切る条件をテクスチャ変化と polygon だけにした。
あわせて instance の運搬を record → Float32 配列にし、record の `#` 探索 (lookupField) を一掃。

| N | 第一弾後 (A) | 第二弾後 (B) | 差 |
|---|--------------|--------------|----|
| 500 | 3.11ms (321fps) | 2.62ms (382fps) | −16% |
| 2000 | 6.45ms (155fps) | 4.82ms (207fps) | −25% |
| 5000 | 14.47ms (69fps) | 9.56ms (105fps) | −34% |
| 10000 | 26.85ms (37fps) | **18.71ms (53fps)** | −30% |

- 改修前 (プロジェクト開始時) 比: N=10000 で ~1000ms → 18.7ms = **~53 倍**。
- フラグメントの style 数式は uniform 版の逐語移植 (varying 置換のみ) でピクセル同一を保証。

## R2b: PxSprite「box 列」vs「アトラス 1 クアッド」の同数 A/B (2026-07-21, BenchPx.bench)

シナリオ: 村の villager (6×10・~18 run/体) を黄金比軌道で N 体、box 列 (PxSprite.draw = polygon 列)
と 1 クアッド (PxSprite.drawQuad = regionRect 付き Item.Sprite・アトラスは PxSpriteAtlas.bake →
px_atlas.png を起動時ロード)。区間を box → quad の順に交互に並べ、同一実行内で背中合わせに取る。
`flix run --entrypoint BenchPx.bakeAtlas` → `flix run --entrypoint BenchPx.bench`。

| N | box 列 avg / p99 | 1 クアッド avg / p99 | 倍率 (avg) |
|---|------------------|----------------------|-----------|
| 500 | 16.67ms / 21.37ms (60fps) | **3.05ms / 8.06ms (328fps)** | ~5.5x |
| 1900 | 54.61ms / 67.32ms (18fps) | **8.33ms / 11.15ms (120fps)** | ~6.6x |
| 5000 | 146.36ms / 188.44ms (7fps) | **16.66ms / 18.27ms (60fps)** | ~8.8x |

- 予算 (R3: 動的 PlacedItem < 2000/フレーム、avg < 8ms / p99 < 12ms) に対して:
  N=1900 の 1 クアッドは p99 11.15ms で予算内、avg 8.33ms はわずかに超 (直前区間が
  box 54ms の重負荷なので熱の水増しを含む — 単独実行ならもう少し下がる見込み)。
  box 列は N=1900 で 54.6ms と予算の ~7 倍 — **人型を数百体以上動かす画は 1 クアッドが必須**。
- 村の序章 (数十体・box 列) は予算に遠く、既定モード据え置きで問題ない。
- 検証: 両モードの絵は SoftRaster で全画素バイト一致 (editor_server/test/TestPxSpriteRaster —
  非反転 / flipX とも diff 0)。
