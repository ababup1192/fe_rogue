# 終わらない flix が誰にも見えないまま積み上がる（checkd の逃げ道に上限が無い）

## 何が起きたか（2026-08-19 の実測）

`flix_ge_studio/server` 1 パッケージに、Flix の JVM が 6 本貼り付いていた。

| 中身 | 本数 | 最長 |
|---|---|---|
| 素の `flix check` | 4 | 3 時間 17 分 |
| 素の `flix test` | 2 | 1 時間 40 分 |

`ps` からは見えず `pgrep` / `jps` からは見えた。後から起こした `make test` は
依存解決の直後で 1 歩も動かず、7 回とも「環境に殺された」ように見えた。

## 止まらなかった本当の理由（2 つある。最初の案は 1 つ目を取り違えていた）

### 1. 発散させていたのは予約語（今日の直因・別で解決済み）

`EngineUpdate.flix` が記録の項目名と変数名に Flix の予約語（`from` / `into`）を
使っていた。**Flix はパースで止まらず、壊れた構文木のまま型検査へ進んで発散する** —
赤も警告も出ず、CPU を 1 コア回したまま何時間でも返らない
（`jstack` で `ConstraintSolver2.simplify` に 6 分 50 秒の CPU、G1 の Conc に 153 秒）。

**取り違えていた点**: 最初の案は「素の CLI どうしが `build/` を奪い合っている」と書いた。
奪い合いは起きていたが、**1 本目が止まった理由ではない**。1 本目は最初から自分だけで
発散していて、後続はそれを見て諦め、素の CLI へ落ちて同じ物を踏み直していた。

→ **予約語そのものは `fge flix-reserved`（保存時とコミット時に走る）で塞いだ。**
この案が扱うのは「発散が起きても、誰にも見えないまま積み上がる」方だけ。

### 2. 見えない・上限の無い素の flix を、フックが起こしている

最初の案は「フックは発生源ではない」と書いたが、**これは間違い**だった。

- `hooks/checkd.go:258` `exec.Command(self, "checkd", pkg)` — `--daemon` が付かないので
  入るのは**クライアント経路**（`checkd.go:75` → `clientRun`）
- 常駐と話せない・起動待ちを過ぎた・仕事が `workTimeoutSec`(900) を超えた、の
  いずれかで `client.go:110` `runFallback` に落ちる
- そこは `cmd.Run()` を待つだけで、**上限も、同じパッケージで既に走っているかの判定も無い**
- しかも `hooks/checkd.go:260-261` で **stdio が nil ＋ 切り離し**（`Setsid`）。
  制御端末を持たないので**引数なしの `ps` に出ない**

呼び元は `flixtouch.go:65`（**保存のたび**、常駐が居なければ毎回）と `flixwork.go:104`。
歯止めの `tooBusy`（`hooks/checkd.go:230-249`）が数えるのは state の `pid` ファイル＝
**常駐だけ**なので、素の CLI は何本でも足せる。「間隔を空けて 4 本積み上がる」形と合う。

### 3. 詰まった常駐の port を消して、以後を全部素の CLI に落とす

1. 常駐が `workTimeoutSec`(900) 以内に返せない → クライアントの読み締め切りが切れる
2. `client.go:103` `hooks.DropPort` が、**常駐は生きているのに** port を消す
3. 再試行の `spawnDaemon` は、生きている常駐が `pid` を握っていて起動に負ける →
   port は誰も書き直さない → 起動待ちを空振り
4. → `runFallback`。**以後このパッケージへの全部の呼び出しが素の CLI に落ちる**

`DropPort` の WhyNot（`hooks/checkd.go:136`）は「死んだ常駐の残骸」を想定していて、
**「生きているが遅い常駐」と区別していない**。これが「1 本詰まる → 全員が素の CLI」の掛け算。

なお、クライアントと常駐が**同じ `workTimeoutSec`(900) を見ている**（`client.go:94` と
`daemon.go:531`）ので、常駐が自分でタイムアウトして `-1`（＝「素の CLI で確かめて」）を
返す正規ルート（`daemon.go:533`）はほぼ通らず、必ず上の経路に落ちる。

## 直す（段 0 が本命。A〜C はその上の保険）

### 段 0. 数行で効く 4 つ

1. **`ReserveDaemon` を素の CLI に落ちない口にする**（`hooks/checkd.go:258`）—
   常駐だけを起こす形（`--daemon`、または「温めるだけ」の verb）へ。
   **見えない raw flix の唯一の自動発生源が消える。**
   今は CHECK が飛ぶことで repl が温まっているので、常駐側で最初に repl を起こす手当てが要る
2. **`DropPort` は常駐が死んでいるときだけ**（`client.go:103`）—
   掛け算のラチェットが止まる
3. **クライアントの待ちを常駐より長くする**（`client.go:94`）—
   常駐が自分で諦めて `-1` を返す正規ルートが実際に通る。常駐は repl を落としてから
   返すので、**素の CLI が走り出す前に repl が退く**という、今は成立していない順序が成立する
4. **素の CLI へ落ちる前に、生きている常駐がいないか見る**（`client.go:110` の直前）—
   いるなら落ちない。新しい pid ファイルを作らずに衝突の大半が防げる

### A. 素の CLI に上限を付ける（保険）

- 規約データは **`checkd.fallbackTimeoutSec`**（`checkd.daemon` の下ではない —
  あれは常駐そのものの寿命の値）。`LoadRules` の欠けキー検査にも足す
  （**既定値へ倒さない**のがこのリポの流儀。キーが無ければ止まる）
- 打ち切りは **SIGTERM を先に送る**。いきなり殺すと `lib/cache/**/*.lock` が残り、
  次の 1 回が Maven リゾルバの無限待ちになる（`Makefile:136-141` が既に書いている罠）。
  残ったときは `clean-locks` 相当をこちらで掃く
- 終了コードは **2**（検査できなかった）。1（型エラー）と混ぜない。
  **打ち切った理由を必ず出す** — 書かないと画面が空行 + exit 2 で「無言で落ちた」に見える
- 値は 900 でなく **300 秒**でよい（素の CLI は温まっていないが、正常なら 10〜60 秒の世界）
- プロセスグループごと落とすなら、**Ctrl+C の転送も一緒に書く**。
  `Setpgid` を付けると人の Ctrl+C が `flix` に届かなくなる（今より悪い）。
  なお `bin/flix` は最終行が `exec` なので**ラッパと JVM は同じ pid** — 最初の案の
  「孤児になる」は事実ではない

### B. 1 パッケージにつき flix は 1 本（保険）

- 守る範囲は「素の CLI どうし」ではなく **「このパッケージで flix を回す権利」**。
  常駐の repl 起動（`daemon.go:157`）も同じ権利を取る（実測は repl ＋ 素の CLI の混在だった）
- 仕組みは新規に作らず **`acquirePidFile`（`daemon.go:91-108`）を共有**する
  （`O_CREATE|O_EXCL` → 負けたら生死を見て、死んでいれば 1 度だけ奪う）
- 生死の判定は **`hooks.PidAlive`（`hooks/checkd.go:145-166`）を使う**。
  Windows では `Signal(0)` が `TerminateProcess` に化けるので、あちらは `tasklist` を見ている
- 置き場は `stateDir(r, pkg)`、名前は `fallback.pid`（`runFallback` と grep でつながる）
- **待つか諦めるかは呼び元で分ける**: `ReserveDaemon` の無人の呼び出しは諦める。
  人の `make check` は、先客の pid と経過を出したうえで上限まで待つ
  （黙って exit 2 だと、人は手で `flix check` を打って同じ状態に戻る）

### C. 見えるようにする

- `fge checkd --status` — 常駐と素の CLI を pid・経過・パッケージで一覧
- `fge checkd --stop-all` が素の CLI も落とす（今は常駐だけ）
- **一覧に出ない JVM がある**ことを doc に明記する（下の「残る穴」の 1 つ目）。
  今日、私が `ps` で見えず `pgrep` で見えたのと同じ読み違えを次の人がする

## テスト（Go）

1. `ReserveDaemon` が起こす引数に、素の CLI へ落ちる口が含まれない
2. 生きている常駐がいるとき `DropPort` が port を消さない
3. クライアントの待ちが常駐の待ちより長い（規約データの値の関係を固定する）
4. 上限を超えた素の CLI を打ち切り、終了コード 2 と理由を出す（残骸なし）
5. 2 本目は権利を取れずに諦め、1 本目を殺さない
6. 持ち主の死んだ `fallback.pid` は奪える
7. `--status` が常駐と素の CLI の両方を出す
8. 新しい規約キーが欠けていれば**止まる**（既定値へ倒さない）

## 影響の範囲

- 通る道: `fge checkd <pkg>`（テンプレの `make check` が `CHECKD=1` のとき）・2 つのフック
- **この守りの外**（同じ形の穴が残る）:
  - `Makefile:178-184` `test` / `193-210` `test-par`（既定 6 並列）/ `320` `test-%` は
    `$(FLIX_TEST)` を直に呼ぶ。**同じパッケージの常駐が生きたまま `make test-<name>` を
    打つと今日と同じ衝突**。せめて「`make test-*` の前にそのパッケージの常駐を止める」は
    1 行で入り、効く
  - `Makefile:435` の engine_full の素の `check`（src が symlink の形なので常駐を使えない）
  - `mk/game.mk:79` / `:100`（`CHECKD=0` や `fge` が無いとき）と Windows 固定の `CHECKD := 0`
- 規約キーを増やすので、**Studio 同梱 engine の `hooks.json` の写しも作り直す**。
  `LoadRules` は欠けキーで止まるので、片方だけ古いと `fge` が動かなくなる
